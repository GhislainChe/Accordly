# Accordly database design — Stage 1B

Status: finalized Stage 1B logical design with additive Stage 2A/2B implementation. [Architecture](architecture.md) defines behavior; [security model](security-model.md) defines grants/trust. Sixteen migrations implement 30 private tables. Production delivery and external signing remain disabled. Historical reports map their own validation scope; logical entities not present in migrations remain requirements, not implied enforcement.

## Stage 2B account foundation

Migrations `20261112001500_account_onboarding.sql` and `20261112001600_recovery_grant_clock.sql` add four private ENABLE/FORCE-RLS tables (30 domain tables total):

- `account_onboarding`: one row per principal; bounded full name, work kind, purpose, positive revision, completion timestamp, initial/last organization FKs, completion intent digest and guided/existing-member origin. Incomplete metadata is never a membership. A completed row cannot change its initial organization, identity/preferences, intent or completion timestamp through ordinary UPDATE; the last-workspace preference remains mutable and reauthorized.
- `account_receipts`: unique principal/operation/key, canonical request digest, bounded outcome and server commit timestamp. Operations are preferences, complete, use_existing and select_workspace. Append-only; keys are not recycled. Completion intent also prevents a second initial workspace when a refreshed client supplies a new key. Retention/deletion remains an operational policy gate.
- `account_recovery_grants`: random ID, principal, verified Auth session ID, unique secret digest, issue/expiry/consumed timestamps. Ten-minute maximum; credentials/targets cannot change. Migration 016 captures a single timestamp for issue and expiry rather than relying on separate volatile default/explicit clock reads. The grant is consumed before the external Auth update; no distributed atomicity is claimed.
- `account_rate_buckets`: operation/scope/HMAC digest key, hourly window, bounded count and two-hour expiry metadata. The credential role has access only to the current private bucket context. No emails, passwords or OTPs are stored here. Cleanup is not yet automated.

`account_command` is the gateway-only, executor-owned fixed-search-path wrapper. The verified identity assertion follows the existing server trust boundary; the database does not independently query GoTrue confirmation/session state. The server obtains live confirmed Auth identity before invocation. Browser/API roles receive neither schema access nor command EXECUTE. Principal resolution retains the existing Auth FK, active-principal checks and transaction-local identity clearing.

Status initializes only private onboarding state, never an organization. Preferences require strict fields and expected revision. Completion serializes on a principal advisory transaction lock, checks required saved preferences, then invokes the existing organization/member bootstrap and restores actor context before completing the self-scoped row/receipt. Tenant creation, initial owner, organization event and onboarding result roll back together. A conflict cannot silently create another workspace. `use_existing` requires an actual membership and grants no owner role. Selection rechecks membership even before replaying its cached outcome. Revoked initial access cannot use a completion retry to bootstrap a replacement.

Read/INSERT/UPDATE on onboarding state, INSERT/SELECT on receipts, and INSERT/SELECT/consume-only UPDATE on recovery grants belong to the self-scoped NOLOGIN executor. Counter rights belong only to the scoped NOLOGIN credential role. The gateway has allowlisted EXECUTE only. No Auth-table SELECT privileges, public domain RPC, new role assignment API or service-role runtime dependency is introduced. Existing `profiles` remains separate; account full name is onboarding/display metadata, not legal identity or signature authority.

The initial migration backfills only existing registered memberships, not email matches or guest representatives. Last-workspace fallback reads authorized memberships and preserves suspended-organization historical read rights. No-access completion is preserved and returns a safe unavailable state rather than provisioning a new tenant. Existing signed versions/proposals/evidence are untouched; only UI labels distinguish current from formerly effective terms.

## Stage 2A physical additions and transaction protocol

Migrations `20261112001000`–`20261112001400` extend existing drafts, versions, proposals, participants, credentials, consent decisions, receipts, audit and outbox. They add one table, `accordly.proposal_feedback`, with tenant-scoped proposal/slot/receipt FKs, actor/name, kind (`revision_requested`, `rejected`, `withdrawn`), bounded reason and server timestamp. It is append-only, ENABLE/FORCE RLS, with only scope-bound signer INSERT/SELECT and integrity SELECT. Supabase API roles and the gateway receive no table access.

`agreement_versions.schema_version` permits 1 and 2, retaining canonicalization 1. Amendment snapshots include full revised contractual terms, immutable original party snapshots, base version ID/digest and amendment metadata. Existing version bytes, generated SHA-256 digests, signatures and evidence are never rewritten. Submitted drafts gain an integrity-owned update guard. Draft kind/base are immutable. Existing composite FKs enforce tenant, parent, draft, candidate and quorum relationships; version numbers remain unique per agreement under an agreement lock.

New internal functions:

- `principal_active` is a boolean authorizer lookup, unavailable to the gateway.
- `amendment_actor` verifies live registered identity and applicable membership, or the stored session digest/source invitation/idle and absolute expiry/authority revision/representative/principal status. It derives current required representative authority and locks organization then agreement. It cannot be called by browser/API roles or the gateway directly.
- `validate_amendment` and `freeze_amendment` belong to the isolated freezer. Amendment data uses `{draft, requested_change, reason, delta_minor, revises_proposal_id}`. Delta is a canonical signed decimal integer string, absolute maximum 9,000,000,000,000,000. Numeric arithmetic checks base + delta = proposed total exactly, within 1…9,000,000,000,000,000. Same currency, exponent and controlling language are required; existing draft/milestone/deadline validators run again in PostgreSQL. Freezing copies every current required slot, creates an immutable schema-2 candidate and seven-day pending proposal, and records no decision.
- `amendment_command` is the sole gateway-executable amendment wrapper, clearing scope before/after its signer-owned implementation. Read operations are `amendment_list` and `amendment_review`. Mutations are `amendment_create`, `amendment_save`, `amendment_submit`, `amendment_revisions`, `amendment_withdraw`. Draft updates require author and expected revision; submission requires the current base. Lists page frozen history by version number, 50 per page; own unsubmitted drafts are capped at 50 recent rows.
- The existing signing command now supports `invite_access`, `invite_amendment`, target-specific reads and `amendment_approval`/`amendment_reject`, retaining the same live Auth/capability boundaries and local signing gate. Consent challenges now store proposal/version/digest, backfilled from their original immutable slot using the migration administrator (the table owner cannot read through FORCE RLS). Challenge targets cannot change. Proof action permits initial signature, amendment approval or amendment rejection. A reject decision has `affirmative=false`, no typed signing name and separate immutable evidence/reason; it cannot contribute to quorum.

Every mutation locks the organization then root agreement, rechecks authority, and checks a receipt keyed by actor/operation/agreement/key. Matching outcomes replay for 30 days after current authorization checks; mismatched or expired keys conflict. Keys remain reserved and are not recycled; receipt retention/cleanup is an operational gate. Failed transactions create no receipt; unknown HTTP outcomes must retry the same command. No bearer value is stored in receipts. Challenges/proofs remain intentionally one-use; verification retries cannot recover a bearer secret and require a fresh challenge when the response is lost.

Pending amendment → effective requires fresh affirmative decisions from all designated slots for the same candidate. A signer-owned command consumes the last proof, records evidence, marks the candidate effective, advances the root pointer from exactly its base and supersedes pending competitors atomically with audit/outbox/receipt. The deferred integrity validator checks every historical effective proposal's unanimous evidence and the root target. Concurrent final approvals serialize on the agreement. Issuance order does not establish priority. Failed COMMIT restores evidence, proofs, pointer and competing proposal states.

Pending → rejected occurs through a fresh verified reject decision or an explicit revision request with immutable feedback; pending → withdrawn is author-only. Existing decisions are never deleted or transferred to replacements. Closed/stale/expired candidates cannot accept new approvals. Read-time expiry does not rewrite history. Unredeemed invitations and unused proofs for closed competitors are revoked; valid consumed sessions remain agreement-history capabilities until their own source/session expiry or revocation. Access invitation reissuance does not invalidate existing consumed history sessions. Security/operator revocation of a source invitation removes derived capabilities; ordinary pending-amendment invitation management targets unredeemed tokens and preserves consumed active-history sessions; active effective-history invitations remain protected from ordinary issuer revocation.

The provider projection returns `effective_version_id` and an explicit effective version independently of its last-100 issued-version history, and filters current signature summaries to that version. This prevents displaying a pending candidate as the current contract. Historical amendment terms, signatures and feedback are read through authorized proposal review. No remote database or exposed-schema table is introduced.

## 1. Schemas, types and ownership

Keep domain records in unexposed `accordly` and callable server functions in unexposed `accordly_commands`. Separate a NOLOGIN migration/table owner from the NOLOGIN command executor. The login gateway can CONNECT and execute named entry points only. Domain tables have ENABLE and FORCE RLS. No PUBLIC, anon, authenticated, or generic service-role domain grants; do not expose these schemas through PostgREST, GraphQL, Realtime, or generated views. `auth.users` and `storage.objects` remain Supabase-managed, with separately reviewed integration policies.

Use UUID primary IDs generated server-side and `timestamptz` database timestamps. IDs are identifiers, not secrets. Every agreement-scoped row includes `organization_id` and `agreement_id`, with composite foreign keys to `(organization_id, agreement_id, id)` on its parent. An agreement's organization is immutable. Avoid cascading deletes on any evidence or history path. Use NOT NULL and closed state/role checks; unknown enum values fail. Index foreign-key lookup columns explicitly. Do not use user-editable JWT metadata as permission data.

Amounts use nonnegative `bigint` minor units with an explicit product ceiling of 9,000,000,000,000,000 per total/line; issue requires total greater than zero initially. Decimal integer strings cross JSON boundaries and are checked before bigint conversion. Currency metadata specifies exponent 0..4, enabled-for-new-issuance flag, and revision; version snapshots preserve exponent even if the catalog later changes. Only XAF/exponent 0 is initially enabled. `1000 XAF` is stored as `1000`, not `100000`. Reject fractional XAF, negative values, overflow and unsupported new currencies. No FX conversion is implied.

Dates use a tagged representation: either `date` for date-only deadlines, or UTC `timestamptz` plus IANA timezone for instants; exactly one form is allowed. Validate timezone names on input. Freeze locale, content language, deadline meaning, precision, and money fields. Never compare localized date/amount strings. The currency and date rules apply equally to drafts, milestones, and amendment candidates.

## 2. Proposed tables and relationships

### Reference data

- `currencies`: three-letter ISO code primary key, numeric code, minor-unit exponent, enabled-for-new-issuance flag, metadata revision and source date. Seed only XAF/950/exponent 0 as enabled initially. Disabling or updating reference data never rewrites frozen version snapshots. Adding a new currency requires reviewed metadata and validation fixtures, not a schema redesign.

### Identity and tenancy

- `principals`: stable ID, kind `registered`/`guest`/`system`, status `active`/`disabled`/`tombstoned`, nullable unique `auth_user_id`, created/disabled timestamps. An active registered principal requires an Auth link; guest never implies an Auth account. Revocation is independent of historical attribution. Use an Auth FK with ON DELETE RESTRICT; a reviewed maintenance command first disables/tombstones the principal and detaches its Auth reference, then permits Auth deletion. It cannot modify immutable evidence snapshots. This avoids an unchecked cascade or a SET NULL that violates the active-principal constraint. Test the procedure against Supabase-managed users before launch.
- `profiles`: one per registered principal, mutable display name and preferred locale. No role, signer authority, or legal identity claim derives from these fields.
- `organizations`: provider tenant, name and administrative metadata. No destructive organization delete endpoint initially; suspension blocks new actions but retains records and controlled export capability.
- `organization_memberships`: organization, registered principal, role `owner`/`admin`/`editor`/`viewer`, active/revoked state, authority revision. Unique organization/principal. Last-owner protection is a locked command, not a count in the browser. Only owners manage owners/admins; admins manage editors/viewers. Membership cannot self-promote.
- `agreement_access_grants`: organization/agreement, principal, grant type, issuing authority, issued/revoked/expiry timestamps. Required for provider editors/viewers; owner/admin has audited organization-wide read access. Client principals receive only explicit agreement/party grants. Membership alone never grants client-party authority. Unique active grant per agreement/principal/type; no email-only visibility joins.
- `agreement_parties`: agreement, side `provider`/`client`, stable party ID, mutable preparation identity only until issuance. Unique `(agreement_id, side)`; initial issuance requires both sides. Frozen versions retain identity snapshots independently of later edits.
- `party_representatives`: agreement/party, intended normalized email, display name, principal binding when verified, authority source, permission flags (`review`, `propose`, `sign`), revocation and authority revision. Assignment to a provider party requires organization authority. Client representative designation is explicit in the proposal and invitation; mailbox verification proves contact possession, not corporate authorization. Changing the bound identity never rewrites a frozen participant slot. Same natural person representing both parties is unsupported initially and rejected at issuance/binding (principal/email checks cannot detect undisclosed aliases).

After activation, provider administration cannot revoke client party authority or historical access. Request-access can issue only a new short-lived capability to an existing representative's stored address, never change that grant. Session revocation is distinct from authority replacement. Implement an audited incident suspension capability separately from organization administration; keep signer replacement unsupported until its consent/recovery policy is reviewed.

### Agreement content and workflow

- `agreements`: organization, ID, creator principal, lifecycle `preparing`/`awaiting_signatures`/`active`, nullable `effective_version_id`, nullable `pending_initial_proposal_id`, monotonic revision, created/updated times. `active` requires an effective version; other states forbid one. Awaiting requires exactly one pending initial proposal. Composite deferrable references permit atomic pointer changes without cross-agreement links. Do not permit arbitrary state/pointer updates.
- `agreement_drafts`: organization/agreement, draft ID, kind, nullable base version, author party/representative, bounded typed payload, revision and timestamps. Initial kind requires no effective base; amendment kind requires a current effective base. One current initial draft per agreement; multiple amendment drafts may coexist. Compare expected draft revision when editing/submitting.
- `agreement_versions`: organization/agreement, ID, unique sequential agreement version number allocated under the agreement lock, kind, nullable parent/base version, schema/canonicalization versions, canonical UTF-8 bytes, 32-byte SHA-256 digest, amount/currency/exponent, content language, created/frozen times, origin draft ID/revision. A version is immutable from INSERT; only draft records are editable. Every candidate, including a rejected one, remains a version. Unique version numbers do not mean all versions became effective. Store integers as strings in canonical JSON; no floating-point contractual numbers. Validate canonical bytes against normalized columns and child projections when freezing; database digest is computed over those bytes. Canonicalization correctness needs fixture tests, not reliance on JSONB serialization order.
- `version_milestones`: version-scoped ID, ordinal, description, amount, deadline and acceptance terms. Unique `(version_id, ordinal)`. If milestones exist they allocate the whole total; an issuance command sums using exact arithmetic and requires equality. Zero allocations are allowed for non-billable milestones, but the agreement total stays positive. Same currency/exponent as the version. Immutable with the parent snapshot.
- `agreement_proposals`: organization/agreement, ID, kind `initial`/`amendment`, unique candidate version, nullable effective base version, proposer principal/party, lifecycle, submitted/expiry/terminal timestamps, explanation and frozen diff. No `draft` state here: submission creates a pending proposal from a draft. Initial base is null; amendment base equals the candidate's parent. Expiry must be after submission and no later than the product's configured issuance horizon. Partial unique index on agreement for pending initial kind. Multiple pending amendments are allowed.
- `proposal_participants`: organization/agreement/proposal/version, immutable required slot ID, party/representative, expected email and identity snapshot, consent wording/version and content language. Unique `(proposal_id, representative_id)`; at least one slot per party and all slots are required. Enforce the minimum and correspondence to canonical bytes in the locked issue command; a row CHECK cannot express cross-row quorum. Initial issuance designates representatives; amendments copy the effective version's required set unchanged. No late slot insertion, reassignment, or deletion.
- `consent_decisions`: organization/agreement/proposal/version, slot, principal and verified identity snapshot, decision `approve`/`reject`, action `initial_signature`/`amendment_approval`, submitted digest, explicit consent/disclosure version, typed name for a positive decision, verification proof ID, database decision time, command receipt ID. Unique `(proposal_id, slot_id)` and unique consumed verification proof. Original signatures are positive initial decisions; amendments use positive amendment decisions. Rejecting is not a signature. SQL checks enforce compatible proposal/action kinds and affirmative disclosure for approval; command checks enforce eligible actor, current state, one-use proof, and exact hash. No participant can edit or retract evidence; changing one's mind closes/replaces the proposal through defined commands, not UPDATE of a decision.

There is one final decision per slot in an issuance. A participant that already approved cannot submit a second reject for that slot. Issuer/proposer withdrawal before effectiveness remains available under its defined permission; otherwise a new/replacement proposal needs fresh decisions. This is workflow behavior, not a legal conclusion about withdrawal of consent. Revoked authority suspends future actions but never deletes a recorded approval.
- `private_evidence_metadata`: one-to-one decision, bounded user-agent and optional trusted-ingress IP or privacy-preserving representation, capture policy version and independent expiry. These fields are excluded from ordinary party receipts. Strip untrusted forwarding headers; never collect IP from caller JSON. Deletion/redaction under reviewed retention does not alter canonical contract bytes or the core decision record.

There is deliberately no duplicate `amendments` state table: a proposal with kind `amendment`, its base/candidate and decisions is the amendment record. Exports must show original effective proposal, every effective amendment, rejected/withdrawn history as authorized, and the current effective pointer, without mislabeling an approval as a new original signature.

### Invitations, capability sessions and delivery

- `invitations`: organization/agreement, proposal/slot or representative target, intended email, allowed actions, public locator, unique 32-byte token digest, hash format version, issued/expiry, consumed/revoked times, issuer and delivery generation. A proposal invitation may only authorize its frozen slot/version; an access invitation authorizes the existing representative's bounded agreement grant. No invitation grants tenant membership/admin rights. Terminal states are exclusive. Reissue revokes the predecessor and dependent challenges/sessions in the same transaction.
- `email_challenges`: invitation or existing verified session, intended representative/email, purpose, proposal/digest/action where applicable, unique challenge locator, code HMAC and key ID, expiry, failed-attempt count, consumed/revoked times. Atomic failed-attempt increments survive a failed verification response; do not raise a rollback-producing exception after incrementing. Resends invalidate earlier challenges; success, exhaustion and expiry cannot be reset by a retry. Challenge proofs are random, short-lived, one-use rows bound to the exact actor/session and consent target, with unique consumption by a decision.
- `verification_proofs`: principal, organization/agreement, registered Auth verification/session binding or guest session, challenge ID, unique random proof-secret digest, proposal/version/digest/action, verified/expiry/consumed/revoked timestamps. Proof expiry is at most 5 minutes after verification and no later than source capability/proposal expiry. A successful challenge creates one proof; a positive consent decision consumes it exactly once. Proof IDs without the correct secret and actor/session binding grant nothing. Store only its digest, never log the raw proof. HMAC input for the source short code includes challenge ID, intended identity, purpose and target digest; the private gateway computes the candidate HMAC using its secret, and the transaction compares it and updates attempts atomically.
- `guest_sessions`: principal, organization/agreement/representative, invitation/grant source, unique secret digest, issued/last-seen/absolute-expiry/revoked timestamps and capability generation. Never store the raw cookie. Idle expiry, absolute expiry, source revocation and authority revision are checked in the database on every read/write; no trust in cookie lifetime alone. Membership/session revocation serializes with consent checks. Consumed invitation revocation cascades logically to its derived guest sessions and unused proofs, without deleting evidence.
- `abuse_counters`: keyed invitation/recipient/IP/global policy bucket, count/window/expiry and policy version, with atomic increments and bounded cleanup. Use keyed pseudonymous email/IP identifiers where possible, no raw secrets. A new challenge or browser session does not reset the recipient/IP bucket. Apply these controls before costly email or hashing work; database challenge-attempt counters remain authoritative for one-time verification.
- `command_receipts`: organization/agreement, actor/capability scope, operation, idempotency key, canonical request digest, outcome reference and committed time. Unique `(actor_scope, operation, idempotency_key)` with agreement/version included in the request digest. Same key/different payload returns 409; same key/same payload returns the authorized original result. Never return a stored result to a newly unauthorized/revoked actor. Initially retain successful signing/approval command receipts with evidence; expire purely operational receipts under an explicit policy. One signature per slot remains protected even after a receipt expires.
- `outbox_events`: organization/agreement, unique event/deduplication key, type, opaque bounded references, encrypted delivery payload/key ID when necessary, status, attempt counter, lease owner/expiry and next attempt. Claims use locked leases/skip-locked semantics; complete/retry requires the current lease generation. Delete encrypted invite/OTP payloads after delivery or expiry, and never include plaintext in error messages. Transport is at least once; recipients may receive duplicate notifications, not duplicate domain decisions.

### Documents and audit

- `document_artifacts`: organization/agreement/version, ID, kind `attachment`/`signed_render`/`translation`, randomized immutable object path/bucket ID, source digest, object SHA-256/size/MIME, render/template/language versions, lifecycle `quarantined`/`verified`/`sealed`/`failed`, created/sealed time and retention hold. Unique bucket/path; no overwrite/upsert. Only verified, sealed attachment identities may enter a frozen snapshot. Signed renders are derived from frozen bytes; generation failure does not roll back signing. A signed PDF digest differs from the canonical JSON digest and both are recorded.
- `audit_events`: organization/agreement, monotonically allocated per-agreement sequence, unique event ID, command receipt, actor/party snapshot, event type, server time, affected proposal/version/digest, allowlisted details, prior-event hash and event hash. Unique `(agreement_id, sequence)` and command/event-purpose deduplication. Executor has INSERT only through trusted commands; no UPDATE/DELETE/TRUNCATE or cascade from user/organization deletion. Hash chain helps detect accidental/application tampering, not privileged rewriting. Periodic signed checkpoints to independently controlled immutable storage plus restore checks are required before claiming tamper evidence against operators; not implemented now.
- `security_events`: restricted operational telemetry for failed access, throttling and credential anomalies, with minimized identifiers, correlation ID and retention class. It is a separate sink/transaction from rejected domain commands; log failure handling must not expose tokens or result in a false successful signature response.

## 3. Index and constraint plan

- Unique constraints: auth-user principal binding; memberships; agreement/version number; proposal/candidate; participant slot; decision/slot; verification-proof consumption; token/session digest; command idempotency scope; object path; audit sequence. Add indexes for all composite FK prefixes used to resolve scoped children.
- Access queries: memberships `(principal_id, organization_id)` where active; access grants `(principal_id, agreement_id)` where not revoked; representatives `(principal_id, agreement_id, party_id)` and intended-email lookup limited to verification commands. No global client email search API.
- Workflow: proposals `(agreement_id, state, base_version_id)` and pending initial unique partial index; decisions `(proposal_id, slot_id)`; participants `(proposal_id, party_id)`; versions `(agreement_id, version_number DESC)`; audit `(agreement_id, sequence)`.
- Credentials: unique digest lookup, plus `(expires_at)` and `(agreement_id, representative_id, revoked_at)` for revocation/cleanup; challenges by purpose/session and expiry; attempt/rate-limit counters keyed by bounded policy scope. Do not use volatile `now()` in partial-index predicates; query expiry as an additional filter.
- Workers: outbox `(status, next_attempt_at, id)` and lease expiry; artifacts `(state, created_at)` for reconciliation. Preserve sealed references and legal holds during cleanup.
- Use CHECKs for row shape, length limits, currency/exponent/amount bounds, exclusive deadlines, decision/purpose shapes, valid terminal timestamps and SHA-256 length. Use composite FKs for relational tenant isolation. Use restricted command functions and immutable-row triggers for cross-row sums, signer quorum, effective-pointer state, state transitions and canonical equality. Deferred constraint triggers may validate end-of-transaction pointer consistency; avoid claiming a CHECK can inspect other rows safely.
- Revoke DML before adding endpoints. Do not rely solely on application validation or RLS to enforce immutable history. Even the command executor cannot UPDATE/DELETE frozen versions/participants/decisions/audit rows; narrowly scoped lifecycle/pointer writes are on separate tables. Migration owner can bypass safeguards and needs separate audited operating controls.

## 4. Transaction protocols

Lock order is organization, agreement, relevant membership/access/representative authorization rows in stable ID order, proposals in ID order, invitation/session/challenge/proof rows in ID order, then receipt/evidence/outbox. Take FOR SHARE locks on organization/authority rows when checking rights and FOR UPDATE when changing them; key-share locks alone do not serialize non-key revocations. Commands spanning organizations/agreements lock them in stable ID order. Membership changes/organization suspension take the organization lock first and do not subsequently take agreement locks; commands observe either the authority before revocation commits or after, never an unguarded cached check. Last-owner checks occur under that exclusive organization lock. Avoid opposite-order locks in workers. Use short transactions, lock/statement timeouts and bounded retries only for recognized serialization/deadlock failures. READ COMMITTED with explicit locks is the initial isolation policy; use SERIALIZABLE only where tests show it is required.

### Freeze and issue

Lock agreement and authoritative actor grants; verify expected draft revision/base. Lock and validate attachments as sealed. Bound sizes, supported currency, dates, both parties and nonempty frozen quorum; canonicalize and verify canonical bytes/digest. Insert immutable version, milestone projections, proposal, participant slots, invitations and encrypted outbox payloads. Withdraw any replaced pending initial proposal and revoke its capabilities. Change initial lifecycle/pointer, increment revision, append receipt/audit, then commit. Failure leaves no half-issued version visible. Notifications happen after commit.

### Verify invitation or consent challenge

Look up locator without revealing existence. Determine agreement, acquire locks in the prescribed order, and recheck token HMAC/digest, attempts, expiry using `clock_timestamp()` after lock acquisition, revocation, delivery generation and intended identity. For a failed code, commit increment/exhaustion and return a generic failure result. For success, atomically consume token/challenge and create session or action-bound proof, plus receipt/audit where appropriate. Concurrent successes produce one capability. GET cannot run these commands. Rate counters must also commit failed attempts and cannot be reset by allocating a new browser session.

### Sign or approve/reject

Acquire organization/agreement/authority locks, then pending proposal, session and proof in the prescribed order. Validate identity, required slot, exact candidate/base/digest, authority generation, expiry, explicit disclosure, and request digest. Recheck an existing receipt before requiring an already consumed proof or a still-pending proposal so a committed retry can return the original authorized result after activation; current read authorization is still required. Otherwise insert one decision and consume its proof in the same transaction. Count the frozen required set; no empty-set unanimity. On any rejection, mark rejected, revoke unused proposal capabilities and update initial lifecycle if needed.

On the final positive initial decision, activate its candidate and root state exactly once. On final amendment approval, compare-and-swap the effective pointer from the locked base to the exact candidate, mark effective, supersede all other pending amendments against the prior base, and revoke their unused proofs/invitations. Add one audit/outbox effect per committed transition. A competing final approval either sees its original committed receipt or receives a stale/superseded conflict. It cannot reuse approval on a new base. Return conflicts safely; no success if the transaction rolled back.

### Revoke, withdraw, expire and retry

Revocation locks the same agreement and capability rows as signing. Whichever transaction obtains the relevant locks first defines the order; committed signatures are not retroactively deleted by revocation. Time is sampled after lock wait so an expired proposal cannot be approved using an earlier transaction start time. Workers materialize expiry only; commands enforce expiry independently. Terminal proposals cannot reopen.

Delivery/render workers claim outbox leases transactionally, do external work after commit, then record outcomes with the lease token. Use deterministic artifact job IDs and unique paths to reconcile an upload that succeeded before a timeout; never upsert over a sealed object. Cleanup is a separate least-privilege job, excludes sealed/held objects, and has dry-run/audit safeguards.

## 5. RLS and proof obligations for Stage 1C

Stage 1C.1 adds a NOLOGIN `accordly_integrity` validator role for deferred constraints, `organizations.kind` for individual/business tenants, and an append-only `organization_events` stream for operations predating an agreement. The registered bootstrap trusts only a private gateway assertion and FK-valid Auth ID; live session/email verification stays at the server boundary, not in a database session emulation. Stage 1C.2 supplies that verified server gateway and an internal frozen-version INSERT constructor; activation/effectiveness and frozen-content updates remain blocked. The remaining logical entities above are not automatically present in the migrations.

Registered identity assertions are accepted only by private gateway-executable functions after server Auth verification; guest identity comes from digest lookup. Functions set transaction-local context internally from those results, not from HTTP/JWT metadata or arbitrary JSON fields. Executor policies require the correct organization and agreement and the relevant active grant; command bodies additionally check operation, state and consent. A nonrecursive security helper may read only membership/grant metadata with a fixed search path; never give it general document read privileges. An RLS helper must not turn a client-supplied organization ID into authority.

Bootstrap lookup cannot depend on a principal context that does not exist yet. Use narrowly scoped internal credential-resolution routines with their own NOLOGIN lookup role and RLS policies confined to the supplied locator/secret digest. These routines can resolve invitation/session/challenge metadata and principal bindings only, never contract content. They are callable only by command functions, not by the gateway/browser directly, and return generic failure until purpose/expiry/revocation checks pass. Set transaction-local lookup scope inside the routine, clear it before domain access, and test that calling another command cannot inherit it. Registered bootstrap similarly maps only a trusted verified Auth assertion to an active principal. Do not solve the bootstrap problem with table-owner/BYPASSRLS execution or a globally permissive credential-table policy.

Prove with real roles: browser anon/authenticated cannot execute command functions or read/write private tables; gateway cannot directly SELECT/INSERT/UPDATE arbitrary rows; executor cannot cross a derived actor's scope; workers cannot act as signers; a reused pooled connection has no prior actor context. Test spoofed organization/user/slot/object IDs, disabled and removed users, unknown JWT users, cross-tenant composite references, direct REST/RPC/GraphQL/Realtime paths, and unexpected function grants. Test immutable UPDATE/DELETE/TRUNCATE attempts, concurrent final approvals, replay, expiry after lock waits, duplicate commands with changed payloads, partial external failures and backup restoration. ## 6. Stage 1C.2 physical mapping and preparation protocol

Migrations `20261110000400_preparation_support.sql` and `20261110000500_agreement_commands.sql` extend the existing tables/roles without replacing the first three migrations. `command_receipts` has a unique `(actor_principal_id, operation, resource_id, idempotency_key)` boundary, immutable request digest/result, agreement/tenant FKs and server-generated thirty-day expiry. `audit_events` has unique agreement sequence, receipt binding, canonical event bytes, prior hash and derived digest. `outbox_events` has composite tenant/agreement/receipt FKs, bounded state/lease checks and no enabled worker privileges. All three FORCE RLS and deny browser/API roles; receipt/audit mutation is append-only.

The gateway can execute new `authorize_operation`, `execute_preparation` and `agreement_details` entry points, never internal validators/canonicalizers/freezer. A NOLOGIN `accordly_freezer` role owns only the internal freeze constructor and receives scoped SELECT, root-row locking and frozen-table INSERT privileges. It cannot update/delete frozen content; the ordinary executor still cannot insert frozen versions. Existing low-level infrastructure commands remain SQL-compatible, but the receipt-backed HTTP protocol is the only new preparation mutation interface.

Preparation lock order is organization SHARE, agreement UPDATE (for existing resources), idempotency transaction advisory lock, then relevant child rows. Authorization is repeated under these locks. The canonical request digest binds actor, operation, resource, typed input and any server-derived provider email. Matching authorized retries return the stored result before checking changed lifecycle/revision; changed payloads or expired receipts conflict. Expired records reserve keys until a separately reviewed archival/tombstone policy exists. Failures roll back all rows; no receipt means no committed success. A lost commit response is resolved with the original key rather than automatic regeneration/retry.

Draft payload schema version 1 permits XAF integer minor-unit strings, explicit exponent zero, positive total up to 9,000,000,000,000,000, bounded terms/scope, en/fr language, tagged date or UTC instant with IANA timezone, and up to 50 exact-summing ordinal milestones. Attachments are rejected. Every update compares the root revision. Party changes are initial-preparation-only, cannot reassign ownership or privileged tenant roles, and cannot self-verify/bind the client. Scoped access management requires owner/admin; active grants require eligible membership or an already verified client representative. Revocation can remove stale grants after membership removal.

Freeze validates both party sides, nonempty required signer sets, distinct cross-party signer identities/mailboxes, current provider membership and complete payload. Under the root lock it constructs a deterministically ordered schema-versioned snapshot, canonical UTF-8 text and SHA-256 digest, inserts immutable version/milestones/pending initial proposal/required slots, advances root revision/pending pointer, then writes receipt/audit/outbox in the same transaction. The proposal expires after seven days; no proof, decision or consent is inferred. Node independently verifies SQL canonical bytes/digest before commit. JCS comparison is restricted to this fixed ASCII-key contract schema; money/revisions use strings and numeric metadata stays within safe integers. Active/effective guards remain unchanged.

## 7. Stage 1C.3 physical signing mapping

Migrations 006/007 add invitations, email challenges, guest sessions, verification proofs, consent decisions and abuse counters, all FORCE RLS. Existing receipt/audit operation constraints and outbox event types are extended additively. Locator-only `accordly_credentials` has no document access; `accordly_signer` derives a tenant/agreement scope from a checked source, receives no frozen-content write privileges and cannot be assumed by the gateway. Public gateway commands are `signing_command` and `signing_rate_limit`; internal resolver/implementation/verification-audit functions are not executable by API/gateway roles. Context is cleared per command and transaction.

Invitations bind one immutable frozen slot and intended email with unique domain-separated secret digest, capped expiry, consumption/revocation and reissue invalidation. Sessions bind source invitation, principal, representative/authority revision, secret digest, optional verified Auth session, idle/absolute expiry and revocation. Challenges bind invitation/session/purpose and immutable keyed-HMAC identity, failed attempts (max five), key version and consumption. Source slot/version FKs bind target identity/digest indirectly through the immutable unique challenge ID; no mutable caller target enters code verification. Proofs bind exact session/principal/challenge/proposal/version/digest/action and a unique secret digest with at most five-minute validity. Secret values/codes never enter receipts/audit/outbox.

Consent decisions are append-only, unique per slot and proof, and bind exact digest/disclosure, affirmative action, typed name, server time and canonical evidence bytes/generated SHA-256. A deferred receipt FK allows evidence, proof consumption, root activation and receipt insertion to commit atomically. Deferred activation validation separately requires all frozen slots, exact proof/digest/disclosure/time correspondence, both parties via existing graph checks, effective proposal and exact effective pointer. Only initial affirmative signing is enabled internally; rejection/amendment/replacement commands remain unavailable.

All signing commands take the organization/agreement locks before credential/authority rows; time is checked after lock acquisition. Incorrect code attempts return failure values so they commit before HTTP errors. Shared fixed-hour counters commit in a separate transaction and serialize conflicting increments across gateway sessions. Sign/invite/revoke receipts are scoped by actor/operation/agreement/key; successful verification uses its unique challenge ID for a secret-free receipt/audit reference. Signing receipts remain retained with evidence and are not recycled using the inherited operational expiry metadata. Replays require current capability/authority before returning a point-in-time result. Signature outbox references commit with the same receipt, but production mail/render workers remain disabled. See the Stage 1C.3 report for local-only transport and unresolved recovery/retention/deployment gates.

## 8. Stage 1D provider read projections

Migrations 008/009 add private gateway-callable `provider_workspace(auth)` and `provider_agreement_view(auth, agreement)` projections owned by the existing NOLOGIN executor. They resolve the live server-verified actor, use existing RLS/preflight and clear context. The workspace returns memberships/organizations and at most 200 authorized agreements; details expose existing permitted draft/frozen records, permission hints, frozen slots, redacted signature receipts and at most 100 allowlisted activity entries. Missing/inaccessible IDs remain indistinguishable. A new scoped decision-read policy and column-level SELECT grant permit only organization/agreement/slot/signing-time/digest projection; raw evidence bytes stay inaccessible to the UI executor. No table, mutation command, bypass role or exposed RPC is added. Exact signing and authorization checks remain in the Stage 1C transaction layer; UI controls never constitute authority.
