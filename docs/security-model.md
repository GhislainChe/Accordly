# Accordly security model — Stage 1B

Status: normative requirements, not a penetration-test certificate. Stages 1C.1/1C.2 implement the private foundation/gateway/preparation; [Stage 1C.3](stage-1c3-report.md) adds initial signing with local synthetic delivery and production disabled. Production delivery, independent guest-history recovery and Storage controls remain requirements. Stage 2B adds the local account/onboarding boundary below. It applies with [architecture.md](architecture.md) and [database-design.md](database-design.md). Default is deny. Every object ID, browser request, forwarded header, cookie and claimed role is untrusted until verified at its boundary.

## 1. Authorization matrix

### Stage 2B account/onboarding boundary

- Anonymous users may submit bounded registration, resend and recovery requests in configured local-test mode. Valid request responses acknowledge eligibility generically without returning users, identity arrays, sessions or existence. Duplicate/unknown/delivery-error requests use the same acknowledgement. A bounded response floor reduces obvious timing differences but does not promise indistinguishable network timing. Verification failures are generic. Native Supabase confirmation/password/rate controls still apply to callers bypassing the application.
- Unverified/anonymous Auth identities cannot pass the live confirmed-account gateway resolver, access onboarding state or create a workspace. Signup itself never creates an organization. Full name in user metadata is display-only and cannot grant a role.
- A verified registered account can read/save only its own onboarding state. Individual/business and create/review/both values are preferences, not grants. Strict inputs reject role, actor, owner, verification and redirect overrides. Completion assigns the verified principal as owner of a newly created tenant through the existing atomic bootstrap; it cannot nominate an owner or adopt a foreign tenant.
- An existing member can complete against an actually authorized workspace, retaining its actual role. A viewer does not become an owner. Last-workspace selection and receipt replay reauthorize membership. On access loss, use another existing authorized membership or a safe unavailable page; never create a replacement implicitly.
- Recovery verification uses the native exact `recovery` purpose; registration verification uses native `signup`. Generic `email` verification is intentionally avoided because GoTrue can accept recovery tokens through that generic type. Fresh recovery issues only the application's dedicated HttpOnly cookie namespace and session-bound one-use proof. Reset requires both, consumes the proof transactionally first, then changes the native Auth password and requests global refresh-session sign-out. A normal app session alone cannot use this application recovery route. Native recovery JWTs retain normal Supabase semantics; cookie separation is not a cryptographically restricted token or a replacement for native Auth policy.
- Registered accounts never inherit guest history by email. Existing guest entry/signing routes remain available without onboarding. Future account claiming must require fresh account and guest-capability verification, explicit consent and per-agreement audited delegation without rewriting guest attribution or frozen records.

Four new private tables use FORCE RLS. The gateway retains no direct table DML; new commands have fixed empty search paths, strict whitelists and self-derived actor context. Shared DB counters commit before native Auth attempts so failures cannot roll back abuse accounting. Targets are HMACs with a separate server key; no forwarded browser IP header is trusted. Local ingress is deliberately conservative/shared; production proxy/IP/CAPTCHA and denial telemetry remain a gate. Public Auth API protections must be configured independently, since a publishable key allows direct native Auth calls.

Local configuration enforces confirmations, 12-character passwords with lowercase/uppercase/digits/ASCII symbols, server-side 72-byte password cap, six-digit OTPs with ten-minute expiry, secure password change and native send/verification limits. Email templates contain codes, not bearer callback links. Verification/reset use POST, same-origin checks, private/no-store/no-referrer and nonce CSP on all new pages. Passwords/OTPs/session/proof secrets are neither logged nor persisted by application code outside secure cookies/native Auth; requests accept no arbitrary redirect destination. Local Auth inbox access is developer-only and distinct from the private guest-signing mailbox.

Registration/recovery remain disabled on external hosts until production SMTP/delivery, CAPTCHA, native limits, trusted ingress, key rotation, incident recovery and browser acceptance are reviewed. Their local-test gate does not configure or secure an unrelated hosted Auth project's public endpoint. Existing signing/amendment production gates are unchanged. Auth and PostgreSQL have no distributed transaction; a consumed recovery grant followed by uncertain Auth failure requires fresh recovery. Existing access-token lifetime and in-flight revocation limitations still apply. Retention/cleanup of account receipts, recovery grants and counters remains operational work.

### Stage 2A amendment authorization additions

- Anonymous or ordinary Supabase `anon`/`authenticated`/`service_role` Data API callers: no private amendment tables or command EXECUTE, regardless of an agreement/proposal UUID or forged GUC/JWT claim.
- Registered authorized agreement reader: effective terms, frozen proposal/history and decision summaries only; no inherited signing or proposal right from tenant ownership. Provider detail returns only its permitted projections.
- Current designated representative with review/propose/sign authority: may author amendments for its own agreement/party. Provider representatives also require active tenant membership and live confirmed Auth with a valid session claim. An authenticated provider cannot sign for the client.
- Verified guest representative: may propose, review, request revisions and approve/reject only within the stored verified capability's agreement and representative binding. Every request checks session/source expiry and revocation, idle timeout, authority revision and principal status. It never becomes a provider tenant member or gains organization access.
- Draft author: may save its own unsubmitted draft with an expected revision, freeze it against the current effective base, and withdraw its own pending proposal. Other parties cannot edit that draft. Frozen drafts/versions/participants and evidence cannot be edited.
- Current required representative without a prior slot decision: may request revisions with a reason, closing the proposal. Approvals are historical and cannot be retracted by changing a draft. Formal rejection uses fresh target-bound verification and explicit rejection evidence; it is not consent to proposed terms.
- Each required signer: only its own designated slot, exact candidate ID/digest/disclosure, fresh action-specific proof and explicit decision. Approval and rejection HMAC purposes differ. Viewing, verifying access, requesting changes and submitting a proposal never imply approval.
- Verified issuer with existing issue permission: local-only private access/amendment invitations for already designated slots. It cannot choose a new representative or broaden a guest capability to another agreement. Provider-independent guest recovery remains absent and is a production blocker.

Both amendment routes use the same server service and database wrapper. Static route code selects registered or verified-session authorization; user JSON cannot assert trusted mode or identity. Guest and signing paths remain disabled for external deployments through `signingConfig`. Local synthetic mailbox is operator-only, with no HTTP code endpoint, analytics or third-party scripts on invitation pages. Secrets remain memory-only/fragment-only and are cleared before requests; no-store/no-referrer/CSP protections are preserved.

Agreement locks serialize proposal creation, negotiation, approval, receipt writes and activation. A current-base comparison and atomic supersession prevent parallel amendments becoming inconsistently effective. Consumed/expired/revoked proofs, rejected/superseded/expired targets and stale digests fail. A replay is authorized before its cached outcome is returned. The signing role is NOLOGIN, has scope-bound RLS and no frozen-content update grants; the gateway has no direct table privileges or membership in that role. New feedback has FORCE RLS and append-only mutation guards. Operators remain trusted; hash chains require separately controlled checkpoints for stronger tamper evidence.

Remaining deployment gates from Stage 1C.3/1D still apply: production transport/reconciliation, independently recoverable client history, trusted-ingress abuse controls and edge limits, Auth ingress hardening, delivery/counter/mailbox cleanup, key rotation, incident handling, retention/legal holds, tested backup/restore and legal evaluation. Existing shared SQL counters remain enabled. Amendments add no production guest-signing enable flag and make no certification, verified legal identity or enforceability claim.

The following rows are the authorization matrix in textual form. Each mutation also requires an active organization/agreement, unrevoked current grants, the correct state/version, and applicable verification. Authorized historical read/export survives organization suspension unless a separate recorded incident restriction applies. No role permits editing signed content, evidence, or audit history.

- **Organization owner**: manage organization and owner/admin/editor/viewer membership, preserving a last owner; read organization agreements and history; prepare/issue initial provider offers; assign provider agreement access and provider representatives. Cannot impersonate a client, alter a frozen quorum, sign without a required slot, or unilaterally amend an effective agreement. Management grants are audited.
- **Organization admin**: read organization agreements/history; manage editors/viewers and their access; prepare/issue provider offers and assign provider representatives. Cannot grant owner/admin status, remove the last owner, modify evidence, or override consent. No access to raw security telemetry by virtue of this role.
- **Provider editor**: read/edit/issue only agreements with an explicit active edit/issue grant. Creation gives its creator that grant transactionally. May assign initial client contact details but cannot grant tenant administration or replace frozen parties/signers. Amendment proposal additionally requires explicit provider party representative authority.
- **Provider viewer**: read only explicitly granted agreements, sealed artifacts and redacted history; no invitation issuance, drafting, signing, approval, membership changes or raw evidence access.
- **Designated provider signer**: must be an active registered organization member and provider representative, with a frozen required slot. May review and explicitly sign/approve/reject only that slot after fresh verification. May propose an amendment if its representative grant permits it. A viewer who is separately a signer gains only these explicit party actions, not general edit rights.
- **Client reviewer**: account or verified guest with an agreement-specific review grant; read only shared frozen proposals/versions, authorized artifacts and redacted history for that agreement. Cannot inspect provider preparation drafts, internal outbox/audit metadata, other clients, organization membership, or raw IP/device evidence.
- **Designated client signer**: reviewer plus explicit client representative authority and a frozen required slot. May sign/approve/reject its own slot with fresh proof, and propose an amendment if granted. Cannot sign another slot, edit a provider draft, issue provider offers, grant organization access or reset the required signer set.
- **Guest before verification**: generic landing/challenge requests only, with invitation proof and throttling; no agreement content or identity metadata. After verification, only capabilities explicitly bound to that agreement/party; no tenant browsing, global search, public Data API access or Storage credentials. Guest invitation issuance for another person is not permitted initially.
- **Delivery/render worker**: claim assigned outbox work, decrypt its bounded delivery payload or render from a frozen version, and publish a validated artifact outcome. Cannot consent, advance agreement state, read arbitrary other jobs, or use the gateway identity assertion endpoint. A separate expiry/reconciliation worker receives only its own command grants.
- **Incident evidence reader**: dedicated, time-bound, audited operational authorization for necessary raw evidence/security events; no consent or domain mutation. This role is not granted to normal organization owners/admins, clients, workers, or routine support. Implement controlled provisioning before any raw evidence collection is enabled.
- **Migration/infrastructure operator**: technical ability to change policies/data/configuration, outside ordinary application permissions. Separate credentials, audit trail, change review, key custody, backups and incident response are required. Do not describe this operator as prevented by application RLS or an ordinary hash chain.

Party access includes the original effective version, subsequent effective amendments, shared pending proposals, and its own authorized decision receipts. Provider-only preparation drafts and private operational evidence are excluded. An amendment author can edit only its own mutable draft; once submitted both parties see the same frozen candidate. Audit receipts expose events relevant to that agreement without publishing secret locators, delivery internals, other tenants, or personal metadata of unrelated representatives.

Before activation the authorized issuer can revoke/reissue pending invitations, but this cannot rewrite an already recorded decision. After activation a provider owner/admin cannot remove client party authority or historical access. The client can request a fresh access invitation to its existing stored representative address through a generic throttled endpoint, without registering or relying on provider cooperation; request-access never grants new rights or reveals matches. A party may revoke its own sessions; compromise suspension is a distinct audited incident capability, not an organization-admin override or signer-replacement shortcut. This operational procedure must exist before external guest signing is enabled.

## 2. Trust boundaries and credential inventory

### Browser and Next.js

Next.js is the policy enforcement entry point, not a trusted input source. Zod bounds shape/length, and services authorize the actor, action, resource and version. Reject unknown object fields on sensitive commands, trust no body-supplied actor/organization flag, and never implement mutation through GET. Return generic 404 for nonexistent or inaccessible agreement/artifact IDs; 401 for absent identity; 403 for a known actor's forbidden action where existence is already authorized; 409 for a visible stale/conflicting command. Invite/OTP errors remain uniform to reduce enumeration. Sanitize errors without dumping SDK responses or tokens.

All cookie-authenticated writes require exact Origin allowlisting and CSRF defenses; SameSite alone is insufficient. Use Next Server Action origin protections plus an explicit policy for Route Handlers, guest exchange and API mutations. Reject unexpected content types, wildcard CORS, arbitrary callback hosts and open redirects. Guest/email challenge endpoints are TLS only and independently rate-limited, including resend and verification attempts. Do not let a Host header build an invitation URL; use a configured canonical origin.

Render contractual content as escaped text or a tightly sanitized allowlisted format. No unsanitized HTML, template execution or remote resource fetching. Apply a nonce-based CSP to future sensitive pages, `frame-ancestors 'none'`, no-referrer, no-store, and no indexing/third-party analytics on invitation/guest/signing routes. The current `X-Frame-Options`/nosniff headers are useful but are not a complete CSP. Protect against malicious attachments (MIME sniffing, active HTML/SVG, PDF content, oversized/zip bombs); force safe content disposition and reject unsupported formats. Do not retrieve URLs supplied in a contract or renderer to avoid SSRF.

### Auth and the current Supabase session implementation

Reviewed source: `src/proxy.ts`, `src/lib/supabase/{browser,cookie-options,proxy,server}.ts`, `src/lib/auth/require-user.ts`, and `src/lib/env/public.ts`.

The existing browser client uses public configuration only. Server clients are request-scoped and guarded by `server-only`. Production cookie options set Secure and SameSite=Lax; browser SDK session cookies remain JavaScript-readable by design. Proxy refreshes via `getClaims()`, synchronizes downstream request cookies and browser response cookies, and preserves no-cache headers. This is session plumbing, not agreement access control. Its returned claims errors are not converted into an authorization decision; protected handlers must deny independently.

`requireUser()` remains an identity-only helper. Stage 1C.2 agreement operations use a separate `getVerifiedIdentity()` resolver: live Auth `getUser()`, valid registered UUID/email, authenticated audience/role, confirmed email and no current ban. Auth/configuration/network failures fail closed. Database principal resolution and operation preflight then enforce active principal/membership/scope; SQL repeats authorization under locks. Confirmed email demonstrates mailbox/account control, not legal identity or company authority. Guests cannot use this registered-only path. A separate verified HttpOnly guest resolver remains required; Auth anonymous users or `auth.uid()` existence never constitute guest consent.

Registered action proofs also bind the validated token's session identifier, obtained from verified claims alongside live Auth verification. Never use an unverified decoded JWT or browser field as that session binding. Guest proofs bind the stored guest session instead.

Proxy applies to non-asset routes except `/`, `/api/health` and the agreement API prefix. Agreement handlers own live Auth verification, request-scoped cookie refresh and safe JSON errors; bypassing proxy does not bypass their guards. Future guest/verification routes need an explicit routing policy with their own capability checks. Auth callbacks need allowlisted redirects and PKCE handling; none exist now. Server Component cookie writes are suppressed only for the known read-only error; other failures propagate. Unit tests simulate refresh; Stage 1C.2 also tests actual local GoTrue cookies and a live ban through production Next handlers. Callback flows, full token-expiry behavior and production ingress remain untested.

### Stage 1C.2 preparation boundary

The server-only `pg` gateway validates the restricted login and TLS configuration, verifies backend role attributes and absence of role memberships per transaction, and uses parameterized static queries, a fixed search path, bounded pool and transaction-local timeouts. Production always verifies database certificate/hostname. Optional plaintext requires an explicit development-only loopback flag. URL parameters cannot override SSL settings. No runtime service-role client is introduced; fixture admin keys exist only in disposable integration setup. The gateway credential can assert registered identities and is therefore a trusted impersonation boundary, not a general-purpose application credential.

Mutation Route Handlers enforce exact configured Origin, reject cross-site Fetch Metadata, require JSON, cap actual request bytes at 128 KiB and body-read time at five seconds, reject duplicate keys/invalid Unicode/deep structures, and apply strict Zod schemas. They accept no actor/principal/owner override. Responses are private/no-store/no-referrer with sanitized errors. HTTP limits do not replace distributed/edge abuse controls. Auth revocation is not atomically coupled to an already executing database transaction.

The new allowlisted commands are preparation-only. Owner/admin manage initial access; editors need scoped edit/issue grants after creation; viewers receive scoped reads. Client reads require explicit verified representative/grant binding; entering an intended client email grants nothing. No external endpoint currently creates that verified client binding. Provider drafts remain private. Frozen signer roles cannot be rewritten; quorum validation rejects missing party sides and duplicate cross-party signers. Freezing records no consent. Old infrastructure functions remain unexposed through HTTP; their compatibility retention does not give them new request receipts.

A separate NOLOGIN/NOBYPASSRLS freezer role receives scoped constructor INSERT privileges only, preserving the executor's original no-frozen-INSERT boundary. No gateway membership permits assuming that role. Receipt/audit/outbox tables FORCE RLS with no API-role grants. Current authorization is checked before replaying receipts, so revoked access cannot retrieve cached results. Thirty-day receipt expiry rejects further replay without recycling the key. Audit events hash exact committed request/version digests and server timestamps; operator-proof checkpoints, denial telemetry and retention policies remain unresolved operational controls.

Do not globally cache clients, principal resolution or authenticated page data. Registered and guest responses are dynamic, private/no-store and CDN-bypass; preserve refresh headers/cookies across redirects and error responses. Public health routes remain credential-free and disclose liveness only. `getClaims()` is not a live session-revocation check. Verify Auth immediately before each sensitive command; a concurrent Auth revocation after verification can still race an in-flight transaction. Domain grant/session revocation is serialized in PostgreSQL; Supabase Auth and the domain database do not share an atomic session-revocation transaction. Keep the verification-to-command interval bounded, and document this residual race rather than promising instant global logout.

### PostgreSQL

Credentials are separated by task:

- Browser publishable key: public Auth integration only; domain and private Storage privileges denied initially.
- `accordly_gateway` login: server secret over verified TLS; CONNECT/USAGE/allowlisted EXECUTE only, no ownership, BYPASSRLS, arbitrary SELECT/DML, role management or public RPC exposure.
- NOLOGIN command executor: narrow table/sequence/function rights for approved commands and explicit RLS; no schema ownership, role creation or access to unneeded operational evidence. Separate helpers expose only necessary membership metadata and must be nonrecursive.
- NOLOGIN integrity validator (Stage 1C.1 refinement): SELECT and organization-row locking for fixed constraint triggers only, with explicit validator RLS policies. No client-callable query function, login, BYPASSRLS, or gateway membership. It evaluates deferred constraints after actor context has been cleared; it does not authorize user commands.
- Worker logins: separate commands for delivery/render/expiry, no identity assertion or signature functions.
- Owner/migration login: offline deployment/administration boundary, never the web runtime.

The gateway authenticates registered requests against Supabase before passing an internal verified-user assertion. It does not forward a client-supplied user ID as that assertion. Guest commands receive a secret digest, derive the principal/capability from stored state and verify purpose/expiry/revocation. Transaction-local actor context is established inside private functions, never in a long-lived pooled session, and is reset by transaction end. Use fixed search paths, schema-qualified objects, minimal security-definer owners and explicit EXECUTE revocation including PUBLIC defaults. A browser must not be able to invoke the same function directly with fabricated assertions. No exposed view, RPC, GraphQL endpoint, Realtime publication or Storage policy may provide a second path around these boundaries.

Both RLS and commands validate organization/agreement identity using composite relationships. UUID unpredictability, a UI filter, a Storage prefix and `getUser()` alone do not stop IDOR. Functions reject attempts to mutate other tenants, rewrite immutable rows, set status directly, broaden grants or consume somebody else's proof. Compare the entire required quorum inside the transaction; do not count approvals supplied by a browser.

### Storage, delivery and operational secrets

Private buckets are mandatory. First release exposes only a download broker that reauthorizes the artifact and streams bounded bytes; neither guest nor browser can choose a bucket/path or mint signed URLs. Recheck authorization for each new download/range request. Restrict ranges/size/concurrency and log only artifact IDs. Downloads already obtained cannot be revoked. Browser roles receive no upload, overwrite, delete or listing grants. Workers seal artifacts after quarantine; only their dedicated operations can change lifecycle metadata, never frozen content.

Supabase secret/service-role credentials bypass RLS. A Storage broker/worker may need one for native Storage operations, but it must be isolated from ordinary domain request handling, must not execute domain commands as an actor, and must not expose arbitrary object access APIs. Store it in deployment secret management with separate access, rotation, usage logs and constrained egress. Because Supabase keys are not bucket-scoped, component isolation reduces exposure but does not reduce the key's inherent privilege. Until this isolation and the broker's authorization proof handling are tested, keep external artifact access disabled. Do not introduce a privileged browser client or reuse a service-role client for ordinary user requests.

Use separate secrets for the database gateway, worker roles, encrypted outbox delivery payloads and short-code HMAC. Raw 256-bit tokens can use SHA-256 digests because of their entropy; six-digit codes require keyed storage and strict online attempt bounds. Keys carry version IDs for rotation; retain decryption keys only for undelivered unexpired payloads. Never persist credentials in audit events, source control, NEXT_PUBLIC variables, exception traces, analytics, request URLs/bodies logged by infrastructure, or crash dumps supplied to third parties. No new credentials are created in Stage 1B.

## 3. Threats and required responses

- **IDOR/cross-tenant access**: derive the actor server-side; use deny-by-default RLS, scoped reads, composite FKs and command authorization; test attacker A with tenant B's agreement/version/proposal/slot/artifact IDs, including list/export/count/error channels.
- **Invitation forwarding or leakage**: high-entropy short-lived token plus mailbox challenge; generic landing, no GET consumption, fragment-to-POST exchange, no-referrer/no-store, redacted logs, no analytics; revoke derived sessions/proofs on reissue/revocation. A compromised mailbox can defeat both same-channel checks and remains a disclosed risk.
- **OTP guessing/replay/session theft**: HMAC codes, atomic attempt/expiry checks and generation invalidation; HttpOnly guest cookies; one-use proof bound to exact digest/action; fresh proof before consent; server-enforced idle/absolute expiry; throttling with global abuse caps. GET scanners cannot consume credentials. Do not automatically sign after OTP verification.
- **Unauthorized changes/privilege escalation**: no browser DML or domain RPC; role assignment restrictions, last-owner protection, explicit signer slots, no signed-field UPDATE, no metadata-derived admin role, no arbitrary user assertion outside the private gateway. Provider access does not mean client consent.
- **TOCTOU/duplicate signing**: fixed lock order and live authorization checks; uniqueness per slot/proof; receipt scope and payload digest; effective-base compare-and-swap; one atomic activation/audit/outbox commit; no empty quorum and no late signer edits. Retry only recognized transaction conflicts, never a failed signature as though it succeeded.
- **Version/document substitution**: canonical frozen bytes, server-computed digests, immutable attachments and slot identities, exact displayed consent target, sealed object hashes and renderer versioning. A PDF, consent checkbox in UI, or typed name alone is insufficient evidence of the recorded workflow.
- **Cache/session confusion**: per-request clients, getUser for sensitive registered operations, no shared cache for identity/data, preserve Set-Cookie and no-cache headers, transaction-local DB context, separate guest cookie namespace and route policy.
- **Stored XSS/SSRF/file abuse**: escaped/sanitized content, CSP, no arbitrary network URLs, quarantine and allowlisted types, safe downloads, parser/render resource limits and worker isolation.
- **Audit tampering/PII overexposure**: append-only grants, transaction-coupled domain audit, separate denied-event telemetry, restricted raw evidence, sanitized receipts, backup/restore checks and externally controlled checkpoints. Application history is not operator-proof by itself.
- **Resource exhaustion/email abuse**: bound payload/attachment/canonical snapshot sizes before hashing, timeouts, rate limits by IP and target, attempt counters that survive errors, outbox leases/retries with maximum lifetime, CI resource limits. Never offer glob evaluation or arbitrary contract-code execution to product users.

## 4. Evidence, retention and access

Core evidence records the exact candidate/digest, principal and party snapshot, intended email, verification channel and timestamp, explicit consent/disclosure wording/version/language, typed name, action, command ID, and server decision time. It must not claim government-ID verification, corporate authority verification or legal certification. Technical UTC timestamps are application evidence, not trusted timestamp authority certificates.

Organizations and clients can obtain their authorized contract history and redacted receipts. Raw IP/device data is separately restricted and minimized, with no automatic organization-admin access. Account deletion disables identity/access and preserves evidence references/tombstones; it cannot cascade through versions or audit. Proposed initial behavior forbids application deletion of signed records. This is not a finalized indefinite-retention policy: production launch requires approved class-specific durations, lawful deletion/redaction handling, holds, backup retention and export rules. Do not collect optional raw metadata before that policy and incident-reader controls exist. Keep one-time secrets/challenges/session records only as long as necessary for expiry/replay/incident needs; purging secret material must not erase core consent evidence.

## 5. Development dependency advisory policy

Re-run full and production-only audits; report command exit codes and actual results in the Stage 1B report. Do not copy Stage 1A's count as a current result. The known [minimatch advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) concerns attacker-controlled glob amplification; the published patch is 11.0.1. The affected copy was in TypeScript lint tooling. Development-only placement reduces production exposure but does not make malicious PR/CI inputs safe.

Do not run `npm audit fix --force`, downgrade a matching Next lint configuration across major versions, or add an untested major-version override to force a green audit. Keep the exact lockfile, isolate untrusted CI jobs from secrets, bound runtime/memory, and prohibit product requests from invoking lint/glob tooling. Track the finding to a compatible upstream lint-toolchain update. Before merging that update, verify peer ranges, audit full/production graphs, and run lint/typecheck/tests/build, including glob handling. ESLint 9 deprecation is a separate maintenance issue; migrate its React/Next/TypeScript plugins together. Open audit findings remain visible release risks, with owner and recheck gate in the report.

## 6. Verification limits

Stage 1D adds actual provider login/logout handlers and protected pages over live Supabase Auth, private workspace/detail APIs and the existing preparation/signing commands. Read projections use scoped RLS and redacted columns; raw evidence is not granted to the UI executor. Each sensitive page response gets a fresh script nonce, no-referrer/no-store and frame/object denial; cookies refreshed by proxy are retained in downstream requests/responses. Invitation URL fragments are cleared before requests, parsed only for the current origin, and kept with one-use proofs in component memory. Contract text is escaped rather than interpreted as HTML. The local mailbox is still private/operator-only. Neither a page load, code confirmation nor checkbox default records consent. Existing attempt, expiry, source/session revocation and unanimous signing gates remain unchanged.

The Stage 1D report separates HTTP/server-rendering integration from browser interaction. Browser tools failed during this stage; no successful browser end-to-end, mobile viewport or assistive-technology test is claimed. Production delivery/recovery/ingress/retention gates remain unresolved and production signing stays disabled. Local HTTP relies on localhost cookie behavior without weakening Secure/HttpOnly; validate it in actual browsers or use a properly trusted HTTPS origin before relying on a demonstration.

Stage 1C.3 adds a separate initial signing boundary. Issuers may invite/revoke only pending frozen slots with current issue permission; tenant administration never grants another party's signature. Provider/registered-bound signers require live Auth user/verified session ID plus their own verified mailbox capability. Guests receive only the designated agreement/representative capability, not tenant membership or ordinary registered API rights. Challenge verification binds the intended client principal without changing the frozen snapshot. Both access binding and fresh proof issuance are independently audited; neither implies consent. The exact disclosure/digest, affirmative action and one-use session-bound proof are checked at signing. A scoped NOLOGIN signer may insert immutable evidence/receipts/audit/outbox and update initial lifecycle pointers; frozen bytes/slots/evidence cannot be updated/deleted by runtime roles. A separate NOLOGIN credential resolver has locator-only metadata/counter access and no documents. Context reset, explicit ACLs and FORCE RLS apply throughout.

Signing is disabled by default and external deployments are rejected by the only implemented `local-test` mode. Synthetic OTP delivery files are private operator fixtures, not a public API or actual external mailbox verification. All shared rate counters are real PostgreSQL atomic counters; the local ingress uses one conservative bucket rather than trusting forwarding headers. Production transport/worker isolation, trusted ingress and denial telemetry, browser HTTPS/fragment handling, access recovery after capability expiry and retention/incident controls remain release blockers. The current guest session cannot recover active history on its own after expiry; provider-independent recovery is required before launch. Production signing must stay disabled until these controls are implemented and verified. Read the Stage 1C.3 report for actual test counts, simulated-versus-live boundaries and residual risks.

The application tests cover public environment rejection and mocked cookie refresh forwarding. Stage 1C.1 additionally has executable pgTAP tests under real PostgreSQL roles, a gateway-login/SET ROLE denial check, retained-role migration replay, and concurrent membership-removal tests. Their exact results are in the report; they do not prove live Auth, guest identity, production TLS/pooling, signing transactions, Storage isolation, legal compliance or email delivery. Future stages require those integration tests before enabling those features. Operator compromise, mailbox compromise, downloaded copies, in-flight Auth revocation, and jurisdiction-dependent retention/authority remain explicit residual risks.
