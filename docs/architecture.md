# Accordly — finalized Stage 1B architecture

Status: Stage 1B design baseline with additive Stage 2A amendments and Stage 2B account/onboarding implementation, 12 November 2026. Stages 1C.1–1D provide the gateway, initial signing and provider/client interface. The user has manually demonstrated the fictional initial-signing flow. Stage 2A browser amendment acceptance is tracked separately in [its report](stage-2a-report.md). Production signing remains disabled. Historical reports retain their own validation scope.

## Stage 2B account and onboarding implementation

Stage 2B adds local account registration/recovery and guided onboarding. Supabase Auth owns passwords, email confirmation and OTP verification. The application uses native, exact-purpose `signup`/`recovery` email codes through POST; templates contain codes rather than callback/bearer URLs. No browser-provided redirect or ownership/role field is accepted. Registered operations retain the approved live-Auth → trusted gateway assertion → private command/RLS boundary; no new runtime Auth-table read grants or service-role client are added. Email confirmation is mailbox control, not legal identity or company verification.

Registration records a validated display-only full name in Auth metadata. It creates no organization. After verification, Step 2 stores full name, individual/business work kind and create/review/both preferences in private `account_onboarding`; preferences never authorize agreement access or signer roles. Step 3 creates the existing approved individual/business tenant and its initial owner atomically with completion and a private command receipt. Creation is serialized per principal; both exact retries and refreshed/new-key submissions cannot create a duplicate initial workspace. Existing actual members may select an authorized existing tenant without changing its roles. Client JSON cannot set an owner or grant membership.

Migration adoption marks pre-existing registered members as onboarded without changing memberships, agreements or evidence. It uses a neutral display fallback if no prior profile name exists, and `both` as a non-authoritative preference. New/incomplete accounts resume their saved step. Completed accounts restore their last still-authorized workspace; revoked selection falls back to another authorized membership, or a dedicated no-workspace page. No new workspace is automatically created after loss of access. Multiple memberships remain separate; a minimal workspace selector persists only an authorized preference.

Account recovery uses a separate Secure HttpOnly Auth-cookie namespace plus a ten-minute, one-use database grant bound to the verified recovery session/principal. Ordinary app cookies cannot invoke the recovery-only endpoint. Supabase recovery tokens remain native Auth sessions, not a new restricted JWT format; cookie separation prevents accidental application-session replacement, while database proof gates the application reset route. Consume the grant before the external Auth password write. Those services cannot commit atomically: a failure or lost response requires checking the intended password or obtaining fresh recovery. Successful password change requests global refresh-session sign-out; existing access JWT/revocation races remain a limitation.

The account service requires local-test configuration with loopback Auth/database/application URLs and fictional `example.test` recipients. Production registration/recovery are disabled pending verified SMTP/delivery, CAPTCHA/native limits, trusted ingress, recovery/incident controls and browser acceptance. Shared PostgreSQL counters enforce per-operation global, conservative local-ingress and HMAC target budgets across instances. Reset targets are derived from the verified recovery account. Native Auth confirmation, password and rate policies also protect direct public Auth calls; application limits cannot replace them. No e-signing or amendment deployment gate is relaxed.

Guest signing stays independent of onboarding. Matching an email, registering, or choosing review/both never reveals guest history. Future claiming requires simultaneous fresh verified account and agreement-scoped guest proof, explicit intent and an audited per-agreement delegation/link. Preserve guest principal IDs, original parties and immutable evidence; never silently merge principals, reassign frozen signers or bulk-grant by email.

History presentation now derives `Current effective` versus `Previously effective · superseded` from the root effective pointer. Historical proposal `effective` state remains intact. Pending proposals never become current because of issuance order.

## Stage 2A implementation decisions

An active agreement's effective version is authoritative; the most recently issued candidate is never assumed effective. Authorized designated representatives of either party may author private amendment drafts. Existing organization read grants allow review, not proposal authorship or signing for another party. Verified guests use the same bounded capability checks as initial signing. Expired guests need a fresh private access invitation and mailbox verification; provider-independent recovery remains an online deployment blocker.

Amendments freeze a full replacement snapshot (schema version 2, canonicalization version 1), a base ID/digest, requested change, reason, signed integer price difference and author attribution. Existing schema-version-1 bytes and signatures are untouched. The currency, exponent, controlling language and complete effective representative quorum carry forward unchanged. The proposed total must equal base plus delta exactly and remain positive; negative and zero differences are supported. Milestones must allocate the revised total. Party replacement and currency/language conversion require a separately reviewed workflow.

Submitted drafts are immutable. Requesting revisions closes the frozen proposal as `rejected` with an append-only `revision_requested` feedback record. A new draft/proposal may link the closed proposal through `revises_proposal_id`; it always starts from current effective terms and carries no approvals. Formal rejection requires its own fresh mailbox proof, exact digest and explicit action; it records a reject decision and reason. Withdrawal belongs to the proposer. Neither revision requests nor withdrawal constitute approval. An already-recorded slot decision cannot be retracted through a revision request.

Multiple pending amendments may share a base. Every mutation locks the organization before the agreement. The first unanimously signed amendment atomically advances the effective pointer only from its own base, closes competitors on that base as `superseded`, and revokes their unused proofs and unredeemed invitations. Issued version numbers express chronology, not priority. Effective proposals remain historical `effective` records; the root pointer identifies the current one. Expired pending proposals are treated as expired at command/read time; no scheduler materializes expiry yet.

Consent challenges explicitly bind proposal, version, digest and action. Existing verified sessions may review and act on another proposal only for the same agreement and representative. Approval and rejection use distinct HMAC purposes and one-use proofs. All designated slots must approve the same candidate before it becomes effective; no automatic proposer consent. Activation, decisions, proof consumption, receipts, audit and outbox commit or roll back together. Closing a proposal invalidates pending authorization for that proposal while preserving already verified, otherwise valid agreement-history sessions. Security/operator revocation of a session's source invitation still removes that session's access. Ordinary pending-amendment token management preserves consumed active-history sessions and revokes only unredeemed tokens, retaining the previous active-client-history guarantee.

Registered and capability routes share one typed amendment service and database command. The static server route chooses the identity path; browser input cannot select trusted actor or capability mode. Mutation receipts use actor + operation + agreement + key, reauthorize before replay, reject conflicting payloads and expired keys, and retain the existing 30-day replay policy. Uncommitted failures leave no receipt. Database operator access and unsigned external audit checkpoints remain trust boundaries.

Accordly is an independent product by BE WISE INNOVATION. It records explicit electronic consent; it does not claim legal certification, verified legal identity, authority to represent a company, or enforceability. Those require separate evaluation.

Read this document with [database-design.md](database-design.md), [security-model.md](security-model.md), and [stage-1b-report.md](stage-1b-report.md). Database design owns constraints and transactions; security model owns permission and credential boundaries. A future change must update all affected documents.

## 1. Binding decisions

1. An organization is the provider tenant. An agreement belongs to exactly one organization for life. Provider and client are distinct agreement parties; a client need not join the provider organization or register an account.
2. All domain reads and writes go through Next.js server services. Domain tables live in an unexposed PostgreSQL schema with deny-by-default RLS and no browser Data API grants. Browser Supabase use is for Auth only initially. Domain mutations are restricted database commands, not independent table writes.
3. Registered identities use verified Supabase Auth users. Guests use server-issued, email-verified, agreement-scoped capabilities and HttpOnly sessions; they do not receive a Supabase service-role key, anonymous Auth account, or a broad JWT.
4. Provider organization membership, agreement visibility, party representation, and designation as a required signer are separate grants. Organization administration never authorizes signing for a client or bypasses an already frozen signer set.
5. Mutable drafts and immutable versions are separate records. A proposal freezes a complete version and its required representative slots before anyone consents. At least one required signer represents each party. Every required slot must explicitly approve; no implicit proposer approval, majority vote, or administrator override.
6. Initial signing and amendment approvals bind to an exact candidate version ID and SHA-256 digest. An amendment candidate exists before approval; final approval advances an effective pointer to that same candidate, rather than creating different bytes afterward.
7. All changes to active scope, amount, currency, deadline, milestones, or terms require an amendment approved by every designated representative of both parties. The initial amendment policy carries forward the current effective signer set. Changing parties or required representatives is out of initial scope: block submission rather than silently changing quorum. Revoked representatives require a separately reviewed replacement procedure, not reassignment by a provider admin.
8. XAF is the initially enabled currency, with minor-unit exponent 0. Use an extensible currency catalog and exact integer amounts, never assumed cents or floating point. English/French locale metadata is supported by design; actual translations are deferred.
9. Signed content, decisions, amendments, and successful domain audit events are append-only for application roles. Database owners/operators remain a trust boundary. Hashes alone do not prevent a privileged operator rewriting history.

Initial issuance gives each designated representative review and amendment-proposal authority for its own party, so both parties retain the ability to initiate changes. More restrictive reviewer-only grants are separate from designated signer grants. Provider administration cannot switch off the active client's proposal right.

## 2. Components and runtime path

Next.js App Router entry points validate bounded Zod inputs, request origin/CSRF defenses, rate limits, identity, authorization, and expected revisions. Server-only feature services will own agreements, guests/invitations, consent, artifacts, and audit. `src/lib` remains infrastructure; the health UI remains minimal.

The command gateway uses a dedicated TLS PostgreSQL login, `accordly_gateway`, with no table DML, no BYPASSRLS, no ownership, and EXECUTE only on allowlisted functions in an unexposed command schema. Its credential is server-only, never a NEXT_PUBLIC variable. Stage 1C.2 uses `pg` with a bounded pool, certificate/hostname verification, transaction-local timeouts and per-transaction role checks. Real local Supabase/TLS integration is tested; hosted pooler/deployment validation remains required.

Command functions use a separate NOLOGIN executor role with narrowly scoped table rights and RLS; the schema owner is different. Revoke EXECUTE defaults for PUBLIC, anon, authenticated, and unrelated service roles. Fix security-definer search paths and qualify all objects. Functions derive an actor from either a registered user identity verified by the trusted gateway, or a guest session digest looked up and checked in the database. The browser cannot supply a trusted actor/context. A compromised gateway could impersonate users; its credential and code are an explicit trust boundary, not something RLS magically fixes.

Database commands recheck membership/capability, same-tenant references, state, expiry, quorum, and expected version under locks. RLS adds isolation for the executor; it does not replace command-level consent and state checks. Read functions set and clear transaction-local actor context too. Never use pooled session-global identity state. Worker logins have separate allowlisted job commands, not gateway or owner credentials.

## 3. Domain and immutable content

An organization has memberships and explicit agreement access grants. An agreement has exactly one provider and one client party initially, a mutable preparation draft, frozen proposals, and nullable current effective version. Parties and representatives are stable application identities; signed versions also contain immutable identity snapshots so profile edits cannot rewrite history.

One proposal model represents initial offers and amendments. Draft kind is `initial` or `amendment`; a submitted proposal points to a frozen candidate version. Required participant slots contain party, intended representative/email, authority basis, and consent disclosure version. Decisions are original signatures or amendment approvals/rejections with explicit consent evidence. Future additions must preserve unanimous approval across both parties.

The canonical signed payload includes scope, exact amount/currency/exponent, deadlines and timezone semantics, ordered milestones, terms, party/representative identities, required slots, attachment hashes, content language, and consent wording/version. Canonicalization v1 uses RFC 8785 JSON canonicalization with amounts encoded as decimal integer strings, normalized UTC timestamp strings, and explicit stable array ordering. Validate schema, bounds, Unicode policy, and canonicalization fixtures in both application and database command implementation before issuance. Persist canonical UTF-8 bytes, digest algorithm and format version; recompute the digest from bytes at freeze. Child rows must equal the canonical content in that transaction. Never hash a live join or a mutable PDF template.

For v1, preserve Unicode strings exactly as displayed: reject duplicate JSON keys, invalid Unicode/lone surrogates, non-finite numbers and unsupported fields; do not apply Unicode normalization during hashing or subsequent rendering/export. Email matching has a separate versioned normalization policy: trim outer whitespace, IDNA-normalize and lowercase the domain, preserve the local part, and never remove dots/plus suffixes or infer alias equivalence. Store both the entered and normalized address. Mailbox verification is to that intended address; an email match never automatically grants access to another agreement. Initial proposals and amendments each expire after 7 days; invitations expire after at most 72 hours within that window. Policy changes apply only to new proposals.

Locale preferences (`en`, `fr`, future BCP 47 tags) do not change identity or authorization. Each issued version has one controlling content language and exact disclosure text. A translation is a separately identified artifact with source digest; it cannot replace signed content. A future bilingual agreement must freeze both texts and their agreed precedence. Dates use ISO representations and preserve the agreed IANA timezone; date-only obligations remain dates, not inferred midnight timestamps.

## 4. State machines

Agreement states are `preparing`, `awaiting_signatures`, and `active` in the initial implementation. There is no direct client PATCH of state.

- Create: enter `preparing`, with no effective version.
- Issue initial offer: `preparing -> awaiting_signatures`; freeze candidate, required slots, expiry, invitations, audit and outbox atomically. Only one initial pending offer exists per agreement.
- Partial consent: remain `awaiting_signatures`; evidence stays immutable.
- Last required positive decision: `awaiting_signatures -> active`; mark proposal effective and point the agreement to its candidate in one transaction.
- Rejection, issuer withdrawal, or expiry before activation: close that proposal and return the agreement to `preparing`. This does not unfreeze or delete the old proposal or its partial signatures. A new proposal needs fresh consent.
- `active` stays active during an amendment. There is no transition back to preparation. Completion, termination, payments, dispute resolution, and signer replacement are deferred features; initial commands must reject them rather than infer consent from admin authority.

Drafts are mutable with optimistic revision checks. Submitted proposals have states `pending`, `effective`, `rejected`, `withdrawn`, `expired`, or `superseded`; terminal states cannot reopen. Proposal kind selects original signature or amendment approval behavior. Only the initial issuer may withdraw an initial pending proposal; either party may reject through its designated representative. An amendment proposer may withdraw its pending proposal, and any required approver may reject it. Expiry is enforced using database time on every command, even before a cleanup worker materializes the expired state.

An amendment is prepared by an active authorized representative of either party against an exact effective base version. Submission validates that base and freezes a complete candidate plus an explanatory diff. The diff is review assistance; the full candidate is the consent target. Pending amendments do not change the contract.

The final unanimous approval atomically sets the amendment effective and advances the effective pointer to its frozen candidate. Concurrent amendments may share a base, but only one can win. Other pending candidates against that base become superseded in the winning transaction. Rebasing requires a new candidate and all new decisions; no approval carries across versions.

## 5. Guest invitations and signing

Guests can review without registration after proving access to the designated mailbox. A link alone does not disclose agreement content. Public invitation landing pages show only generic verification instructions; never client names, amounts, or agreement metadata.

Use a random 32-byte base64url invitation secret, stored as a SHA-256 digest with a purpose/domain prefix and invitation identifier. Default expiry is 72 hours, further capped by proposal expiry. Reissue revokes previous pending invitations. GETs, previews, and email scanners cannot redeem a token or consume an OTP. Prefer a fragment token consumed by a minimal first-party page, POST it over TLS, clear it immediately from history, and use no-referrer/no-store and no third-party resources. Redact request bodies and URL material in every logging layer. Fragments reduce server URL logging but do not eliminate browser, extension, email-provider, or XSS exposure.

Explicit POST starts an email challenge to the immutable intended email, never to a caller-selected address. Require invitation proof plus a fresh code. Six-digit codes expire after 10 minutes, permit at most 5 failed attempts, and use keyed HMAC storage with a dedicated server secret to resist offline enumeration of the small code space. Resend invalidates prior challenges. Defaults: at most 5 sends/hour per invitation and recipient, plus 20/hour per IP, with global abuse caps; tune through a recorded policy change, not a client parameter. Rate limits supplement, not replace, atomic attempts and expiry checks.

Successful challenge verification atomically consumes the invitation, binds the guest to its intended agreement/party capabilities, and creates a random 32-byte guest session. Store only its digest; send it in a host-only Secure HttpOnly SameSite=Lax cookie, never localStorage. Sessions expire after 30 minutes idle or 12 hours absolute, capped by the verified invitation/proposal expiry. Revocation checks the stored grant and session on every request. Failed delivery or lost cookies require a new invitation/challenge; a consumed invitation is never reusable. An authenticated user with matching verified email still needs the intended invitation/party grant; email equality is not a cross-agreement authorization rule.

Signing or approving requires a fresh one-use mailbox verification proof no older than 5 minutes, bound to actor/session, proposal ID, candidate digest, and action. Provider signers additionally require an active Supabase session and current organization/party authority. Verification and signature consent are separate actions; OTP confirmation does not sign anything. The signature command consumes the proof and records the explicit displayed consent, typed name, actor identity snapshot, channel, verification time, server signing time, digest, and policy/disclosure version.

Guests can later propose amendments through a newly verified, agreement-scoped session if their representative grant permits it; old signing links do not become permanent access. Account registration does not automatically merge guest identity, transfer party authority, or change historical evidence. Require fresh verified binding and an audited account-link command for any future linking feature.

To avoid making continuing client access depend on a provider's willingness to resend a link, provide a generic, rate-limited request-access operation using the agreement locator and intended email. It sends a fresh invitation only to an existing authorized representative's stored address, reveals no match/content, and cannot create authority or change the recipient. The same token-plus-challenge verification then applies. Once active, a provider administrator cannot remove client party authority or its access to signed history; only that party's authorized revocation or a separate audited incident procedure may suspend its capabilities. Suspected compromise may revoke sessions immediately but must not reassign a frozen signer. Organization suspension blocks new writes; authorized historical read/export remains available under a separate retention/incident policy.

Mailbox verification cannot establish a human's legal identity, independent second-factor possession, corporate signing authority, or freedom from coercion. A shared/compromised mailbox or provider-entered incorrect identity remains a material risk. Display this limitation without advertising certified signatures. Stronger identity checks and independent factors are future options.

## 6. Transactions, retries, storage and audit

All critical transitions follow the locking/idempotency rules in the database design. No email, PDF render, or Storage network request occurs inside a database transaction. Persist a durable outbox intent with the domain commit. Invite/OTP delivery payloads are encrypted under a separate worker-held key and purged after delivery/expiry; only token digests enter invitation/evidence records.

Private Supabase Storage holds immutable artifacts addressed by randomized object IDs, with version/digest metadata in PostgreSQL. Upload to quarantine, check type/size/content, promote using a worker, then seal the object reference before issuance. Neither browser nor participant can overwrite/delete frozen attachments or signed artifacts. A transactional outbox reconciles Storage and database failures; orphan cleanup cannot delete sealed objects or objects subject to a hold.

For the first implementation, authorize each download and stream it through a server broker; guests never receive Storage credentials. The broker accepts an authorized artifact ID bound to a checked grant, not a caller-selected bucket/path. A narrowly isolated Storage component may require a server-only Supabase secret/service-role credential for object access; that credential bypasses RLS and is not a least-privilege key. Keep it out of the ordinary command gateway, isolate access/network/operations, audit usage, and document blast radius. Prove deployment isolation before enabling this path. Registered-user reads can later use Storage RLS once separately tested.

Do not promise immediate revocation of a signed Storage URL: issued URLs remain bearer capabilities until expiry (or broader signing-key revocation). If introduced later, cap TTL at 60 seconds and remaining grant lifetime and record the residual access window. Revocation cannot retract already downloaded bytes or stop bytes already in flight.

Successful domain audit events are written in the same transaction as the change and ordered per agreement under its lock. Separate append-only security telemetry records denied attempts; it cannot be reliably logged in a transaction that rolls back. Audit details are allowlisted and exclude secrets, full documents, OTPs, and unnecessary IP/device data. Parties see agreement history and redacted consent receipts; raw evidence/operational telemetry is restricted to a separate incident role. Retention is classification-specific, not indefinite by accident: preserve signed records and audit lineage, prohibit application deletion, and block production launch until a reviewed retention duration, legal-hold process, redaction policy, and backup-expiry policy exist. Temporary credentials and encrypted delivery payloads have explicit short lifetimes above.

## 7. Stage 1C gate

Implement migrations and constraints only in Stage 1C. First prove gateway/executor ownership and RLS behavior on a disposable Supabase-compatible database, including direct Data API denial and pooled-context isolation. Then implement immutable snapshots, unanimous transactional decisions, guest tokens/challenges, and private artifact boundaries with adversarial tests. External delivery, real guest signing, and production activation remain disabled until relevant verification, operational retention, and credential-isolation gates pass. See the report for findings and the ordered implementation plan.

## Stage 1C.1 implementation clarifications

- Individual freelancers and businesses both use the same tenant model, distinguished by `organizations.kind` (`individual`/`business`); there is no second personal-data ownership scheme.
- A separate NOLOGIN, NOBYPASSRLS `accordly_integrity` role owns narrowly invoked constraint triggers. Deferred checks must still work after commands clear actor context, so it has validator-only SELECT policies, no query endpoint and no gateway role membership. This supplements, rather than replaces, the executor/owner/authorizer separation.
- Organization bootstrap/membership changes need an audit stream before any agreement exists. Append-only `organization_events` records these operations without inventing a synthetic agreement. Agreement consent/audit chains remain deferred.
- On Supabase, managed Auth grants may not be delegable to a new table owner. Create the Auth-user FK as the migration operator and reassign domain tables to `accordly_owner`. The identity helper does not read Auth credentials or claim to verify a live session; only the trusted future server gateway may assert a user after live Auth/email checks. FK existence is not authentication.
- In Stage 1C.1 the frozen tables had no runtime write path. Stage 1C.2 adds only the internal immutable INSERT constructor described below. Active/effective transitions deliberately fail closed until a reviewed signing migration supplies consent evidence and activation commands. This is a stage gate, not an alternative agreement state machine.

## Stage 1C.2 implementation clarifications

- The registered server resolver calls live Supabase `getUser()`, rejects anonymous/unconfirmed/banned identities, and supplies only verified UUID/email to the restricted gateway. HTTP body actor assertions are rejected. Operation preflight precedes execution; SQL rechecks rights under organization/agreement locks. Agreement handlers perform their own request-scoped Auth/cookie handling, independently of proxy claims refresh.
- Initial preparation supports strict typed create/update/party/access/freeze commands, plus authorized detail reads. Both tenant kinds use the same model. Current party configuration is one provider contact (the verified actor) and one intended client email; it cannot bind a client principal, claim email verification or overwrite a richer verified signer configuration. Existing designated required signers must satisfy full frozen quorum checks. There is no guest consent, delivery, signature or activation endpoint.
- Freezing inserts a pending initial proposal, immutable version/milestones and every required signer slot. A separate NOLOGIN `accordly_freezer` owns this constructor with scoped RLS/INSERT privileges; the ordinary executor retains no frozen-content INSERT/UPDATE/DELETE. No invitation is issued yet. A durable outbox intent records preparation only, with no enabled worker.
- Canonical schema version 1 uses RFC 8785-compatible JSON for the constrained typed snapshot, UTF-8 SHA-256, exact integer strings, stable party/signer ordering and ordinal milestones. Invalid Unicode/NUL, unknown fields, ambiguous deadlines, inconsistent totals and attachments are rejected. SQL constructs and hashes authoritative bytes; the Node implementation independently matches text/digest before commit. SQL key sorting is deliberately limited to this ASCII-key schema, not advertised as a general JCS implementation for arbitrary JSON.
- Successful mutations atomically persist an actor/operation/resource/idempotency-key receipt, root revision, immutable audit event and any outbox intent. Exact retries return the stored result only after current authorization. Conflicting or expired keys return conflict; retained expired keys never become reusable. The thirty-day replay window is not a deletion policy. Failed transactions produce no success receipt; uncertain commit outcomes require retrying the same key. See the Stage 1C.2 report for lock order and limits.
- Audit events bind request/version digests and exact server timestamps into a per-agreement hash chain. The chain is not operator-proof timestamping. Denial telemetry, external checkpoints, retention/hold/deletion, distributed rate limits, hosted pooler behavior and deployment secret/TLS provisioning remain operational gates.
- Migration 004 corrects PostgreSQL default function privileges globally: schema-local default revokes cannot subtract the built-in global PUBLIC EXECUTE grant. Explicit function ACLs and regression tests accompany this correction; original migrations remain unchanged.

## Stage 1C.3 implementation clarifications

Stage 1C.3 preserves the binding model with six private credential/decision/counter tables and two NOLOGIN roles: locator/bucket-scoped `accordly_credentials` and derived-tenant/agreement-scoped `accordly_signer`. Only restricted server entry points assert registered identity or redeem stored capability digests. A provider requires live Auth plus verified session binding; guests require no account. Every frozen slot, on both parties, must have exact affirmative consent/proof evidence before atomic activation. Deferred constraints independently check quorum and evidence correspondence; immutable versions/slots remain unchanged.

Freeze remains preparation; explicit post-freeze invitation issuance locks the root and targets one frozen slot. Invitation reissue revokes source capabilities. Verified guest binding does not rewrite the original null-principal/contact snapshot. A separate fresh challenge precedes each one-use signing proof; mailbox control and consent are separate actions. Verification/decisions are audited, signatures/activation produce durable outbox references, and no worker runs inside the transaction.

The local-only implementation uses a challenge HMAC bound to immutable challenge UUID/purpose, with intended identity/session/version binding enforced through protected rows/FKs. This is an explicit refinement of the concatenated-field HMAC description above; caller fields cannot change a challenge target. SQL counters are shared across processes, with conservative single-ingress local buckets. Invitation/session/proof secrets are stored only as domain-separated digests. Production mail/ingress/denial telemetry, request-access recovery after expiry, rejection/withdrawal/replacement and amendment operations are release gates, not enabled capabilities. Current signed history reads last only while a valid capability remains; provider-independent recovery is still required before launch. See the Stage 1C.3 report for precise limits, tests and next UI stage.

## Stage 1D interface boundaries

Stage 1D adds only restricted provider read projections and Auth login/logout around the existing mutation/signing commands. Server layouts independently verify live registered identity; capability review stays on its separate guest/registered signing path. Workspace/detail/history data are read under existing RLS and allowlisted gateway functions; the UI executor receives signature-receipt columns only, not raw evidence bytes. No client role can call these private functions directly. Permissions are server-enforced, regardless of visible controls.

The interface uses exact canonical review data, a separate fresh code and initially unchecked affirmative consent before signing. Invitation fragments are removed before requests and secrets remain only in component memory; self-hosted fonts, nonce-bearing scripts and no-referrer/no-store pages avoid third-party leakage. Read-only projections do not alter frozen models, quorum, authority or state transitions. Local demo provisioning is infrastructure-assisted and restricted to its own project/fictional identities. External delivery, active-history recovery, production ingress/retention and real-browser/mobile QA remain gates documented in the Stage 1D report.
